# 기술 결정: 크레딧 기반 수익화 구조

**날짜**: 2026-05-10

---

## 배경

AI 기능(음성 메모 자동 분류)에 Claude/Gemini API를 사용하는 서비스 운영 비용이 발생함.  
사용자가 직접 API 키를 등록하는 "Bring Your Own Key" 방식과 크레딧 구매 방식 중 선택 필요.

---

## 결정: 크레딧 구매 방식 (사용자 키 등록 불가)

### 선택한 이유

1. **타겟 사용자 특성**: 비트겟 API를 직접 연동할 정도면 Gemini/Anthropic 키 발급도 어렵지 않음. 키 등록 허용 시 대다수가 직접 키를 쓰게 되어 수익화 불가능.
2. **UX 단순화**: 사용자가 API 키를 발급·관리할 필요 없음. 크레딧 구매 → 기능 사용의 명확한 흐름.
3. **비용 통제**: 서버 env의 단일 키로 관리, 사용량·마진 추적 가능.

### 포기한 대안

- **사용자 키 등록 허용**: 수익화 불가 (기술 허들 낮은 타겟에서 모두 직접 키 사용)
- **월 구독 플랜**: 구독 시스템 별도 구축 필요, 지금 단계에서 과도함. 이후 추가 검토.

## 결제: Toss Payments

### 결제창 방식 (`@tosspayments/payment-sdk`) 선택

초기에 결제위젯(`@tosspayments/payment-widget-sdk`) 시도 → Toss 대시보드에서 위젯 상품 별도 활성화 필요, 401 에러 발생.  
일반 결제창은 표준 테스트 키로 즉시 사용 가능하여 전환.

### 결제 흐름

```
패키지 선택 → requestPayment("카드") → Toss 결제창
→ /payments/success?paymentKey=&orderId=&amount=
→ POST /api/payments/confirm → Toss 서버 승인 → credits increment (트랜잭션)
```

orderId 형식 `{packageId}_{userId}_{timestamp}`: 서버에서 packageId 추출해 금액 검증.  
`tossKey` unique 제약으로 중복 결제 방지.
